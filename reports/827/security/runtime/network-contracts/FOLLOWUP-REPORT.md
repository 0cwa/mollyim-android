## SEC-UP-04 refinement: URL userinfo and fragment

I tested the exact cached OkHttp 5.3.2 client behavior with an HTTPS loopback server, synthetic URL userinfo (`FAKEUSER:FAKEPASS`), and a synthetic URL fragment. The server returned 200. Captured evidence was: `authorization_header_present=false`, `request_target=/resource`, `fragment_was_sent=false`. The response therefore refutes the earlier wording that URL userinfo becomes unintended Basic Authorization in this code path; OkHttp did not synthesize that header, and URI fragments are not sent in an HTTP request target. The fixture contains only fake data. Reproduction: `run-userinfo-probe.sh`, source `UserInfoProbe.java`, output `userinfo-probe.log`.

The target still accepts QR URLs containing userinfo/fragments because the QR parser checks scheme/authority/type and the WebServer branch checks HTTPS, but does not reject those components. Classify that as low-severity input-validation hardening/UX: the QR parser accepts URL components that have no intended transport meaning in this OkHttp path. This probe demonstrates no credential header leak, no fragment transmission, and no new security regression. A focused parser test should assert rejection if the product chooses to disallow those components; preserve the distinction between parser hygiene and demonstrated transport risk.
