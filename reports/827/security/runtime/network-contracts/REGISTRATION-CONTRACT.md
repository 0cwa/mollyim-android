# Registration wire-contract evidence

## Finding

The candidate16 adapter's use of Signal's `DeviceAttributes` for `PUT /v1/devices/link` is supported by the public Signal-Server source contract available at the pinned client dates. The earlier review phrase “server-default/wire equivalence is not proven” was too broad. The relevant extra Molly `AccountAttributes` fields are not inputs to linked-device creation in that server source; the evidence does not depend on guessing defaults for those fields.

## Evidence

- Signal-Server commit [`5e1338a571b734dc1dcdd402d7b92dd6e7a203ed`](https://github.com/signalapp/Signal-Server/commit/5e1338a571b734dc1dcdd402d7b92dd6e7a203ed), committed 2026-04-16, changed `LinkDeviceRequest.accountAttributes` from `AccountAttributes` to `DeviceAttributes`. Its parent [`149de6c4645affb57016e069babbef97fc74196d`](https://github.com/signalapp/Signal-Server/commit/149de6c4645affb57016e069babbef97fc74196d) has the prior type. The new request model remains nested under the JSON property `accountAttributes`.
- The `DeviceAttributes` record at that commit contains `fetchesMessages`, `registrationId`, JSON `pniRegistrationId`, `name`, and nullable `capabilities`: [source](https://github.com/signalapp/Signal-Server/blob/5e1338a571b734dc1dcd402d7b92dd6e7a203ed/service/src/main/java/org/whispersystems/textsecuregcm/entities/DeviceAttributes.java). This is the same set candidate16 serializes from baseline `DeviceAttributes`.
- At Signal-Server commit [`20cf3d7429aca6e535b973d58e9f57cdd3ee4dff`](https://github.com/signalapp/Signal-Server/commit/20cf3d7429aca6e535b973d58e9f57cdd3ee4dff), dated 2026-07-28, `DeviceController` still exposes `PUT /v1/devices/link`, obtains `linkDeviceRequest.deviceAttributes()`, and builds `DeviceSpec` from only `name`, `capabilities`, registration ID, PNI registration ID, and `fetchesMessages` plus the activation request's keys/tokens: [controller source](https://github.com/signalapp/Signal-Server/blob/20cf3d7429aca6e535b973d58e9f57cdd3ee4dff/service/src/main/java/org/whispersystems/textsecuregcm/controllers/DeviceController.java). In particular, it does not use `voice`, `video`, `unrestrictedUnidentifiedAccess`, `discoverableByPhoneNumber`, `registrationLock`, `unidentifiedAccessKey`, or `recoveryPassword` when creating a linked device.
- The same source commit's [SystemMapper](https://github.com/signalapp/Signal-Server/blob/20cf3d7429aca6e535b973d58e9f57cdd3ee4dff/service/src/main/java/org/whispersystems/textsecuregcm/util/SystemMapper.java) configures Jackson `FAIL_ON_UNKNOWN_PROPERTIES` to `false`. Thus extra nested properties emitted by the legacy target `AccountAttributes` representation are ignored by this server source configuration, rather than causing a request parse failure.
- The Signal client baseline pin is `c47a74ba0961903eeaeda6d22347a990056c3e83` (2026-07-10); Molly target is `0e202dda90785771ff8c87526eaaf30c655f54f3` (2026-07-30). Server commit 5e1338 is before both; source commit 20cf3d is two days before the Molly target date. The client's pinned baseline DTO documentation also identifies `DeviceAttributes` as the model for `PUT /v1/devices/link`.

## Conclusion and limit

**Source-level adapter contract: supported.** Candidate16 uses the same nested request property and five fields as Signal-Server's `LinkDeviceRequest`/`DeviceAttributes`; the Molly-only extra `AccountAttributes` fields have no linked-device consumer in the examined server controller, and that server mapper ignores unknown properties.

**Deployed-server compatibility: not established.** No evidence in this review identifies the exact server build/deployment revision serving Signal clients at either pinned client date. The dated public mainline source is strong compatibility evidence, not proof of a production rollout or a live registration. No credentials, real account, or server endpoint were used. Existing local DTO tests verify serialization only; they are not network integration tests.

The exact fetched source snapshots and their hashes are retained in `server-source-evidence/`; `COMMIT-METADATA.json` records the parent, author/committer dates, message, and source paths. The executable comparison is `verify_registration_source_contract.py`; rerun from this directory. It uses candidate16 compiled classes from the candidate worktree whose tree is `24a27bf3ddf2f23593f5a11e3230b66b335bc2a3`.
