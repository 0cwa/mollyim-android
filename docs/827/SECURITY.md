# Security review

## Scope and assumptions

This review covers the UnifiedPush receiver and distributor boundary, lock-screen notification routing, MollySocket provisioning and HTTP calls, plus the Signal linked-device adapter. It assumes the user intentionally selects a UnifiedPush distributor and scans or enters a MollySocket URL. The selected distributor is a trusted push-delivery dependency: it receives the connector registration token and can cause wake-ups, but it should not receive Signal message contents or MollySocket device credentials. The configured MollySocket server receives the account UUID, linked-device ID/password, and push endpoint as part of its connection request.

The exported receiver is required by the UnifiedPush connector. Its manifest has no sender permission or signature check. Connector 3.0.10 checks the registration token against its local registration set and resolves the instance before dispatching callbacks; an absent or unknown token returns without dispatch. The connector does not check the sending package signature. This makes the selected distributor and its possession of the connector token the trust boundary. The receiver accepts connector message payloads as delivery triggers and does not deserialize protected Signal message data.

## Findings and disposition

| ID | Finding | Disposition |
| --- | --- | --- |
| F4 | A locked `NEW_ENDPOINT` or `UNREGISTERED` event previously left `registrationStatus=REGISTERED`. `AccountValues.pushAvailable` derives UnifiedPush availability from that status, so an old registration could suppress WebSocket fallback indefinitely. | **IMPLEMENTED, PENDING TEST EXECUTION.** Locked endpoint rotation and distributor removal now mark only routing availability `UNKNOWN`, restart the network, and post `PushServiceEvent`. The endpoint and device credentials remain untouched while locked. Focused Robolectric tests cover `AccountValues.pushAvailable`, callback effects, and protected-value access; execution is pending the build agent. API 30 historical synthetic tests proved the refresh-job transition from registered to pending/WebSocket availability, but did not cover this callback fix. |
| F5 | Registration failures could leave stale registered availability. Job exceptions can also restart networking on each retry. | **PARTIALLY ADDRESSED.** Callback failures now invalidate stale status and restart the network. Refresh jobs remain capped at three attempts and six hours with at most two instances. The refresh job's retry/recovery and repeated-reset behavior have source review only; live retry timing was not exercised. |
| F6 | The receiver is exported and has no Android sender permission. | **BOUNDED by connector token validation.** The compiled connector checks the supplied token/instance against private registration state before calling receiver methods, but does not authenticate the sender package. A malicious selected distributor can send forged control callbacks. Non-selected apps without the token cannot dispatch through the connector path. Focused Robolectric tests exercise missing and unknown tokens against the inherited receiver pipeline; execution is pending. This is an accepted UnifiedPush trust dependency, not sender authentication. |
| F6 | Lock-screen push payload classification uses string searches for `"urgent":true` and `"test":true`. | **Privacy guarded, payload parsing is brittle.** While locked, the app only posts the generic “may have messages” notice, and only when the existing preference allows it; it does not read or display message contents. Malformed or unexpected payloads can cause false classification or missed wake-ups. The new Robolectric tests cover locked urgent, malformed, and `test:true` payloads but remain unrun; the historical API 30 run covered synthetic message callbacks and notification triggering while unlocked. |
| F7 | Linked-device setup uses the pinned Signal `DeviceAttributes` registration API and initializes signed/last-resort ACI and PNI prekeys before saving the local MollySocket device record. | **Source contract supported; live registration blocked.** The five serialized `DeviceAttributes` fields match the examined dated Signal-Server `LinkDeviceRequest` contract, and the linked-device handler consumes those fields. The deployed server revision is unknown. No real account or server was used. |
| F7 | If linked-device creation succeeds but local prekey loading fails before `createDevice()` returns, the newly created linked device can remain orphaned remotely; the local device ID/password are not yet persisted, so automatic cleanup cannot identify it. | **Residual availability risk, inherited flow.** Retries can create additional linked devices until the server limit is reached. Device-limit behavior, interrupted provisioning, and recovery were not exercised against Signal. A focused transactional provisioning change requires a safe way to persist a recovery handle before prekey loading or remove the new device on failure. |
| F7 | MollySocket credentials are sent in a JSON POST to the configured HTTPS URL. | **Transport controls verified.** The app disables both HTTP and HTTPS redirects for discovery and registration, so the secret-bearing body is not forwarded by an automatic redirect. `MollySocketDevice.toString()` emits only the device ID. The registration DTO probe confirms the password is a body field; it is not a proof of live server behavior. |
| F7 | QR parsing permits HTTPS URLs with userinfo or fragments. | **Low-severity input hygiene.** A loopback probe using the exact cached OkHttp 5.3.2 artifact showed URL userinfo did not create a Basic Authorization header and the fragment was not sent. Thus the previously suspected credential leak is **not reproduced**. Rejecting ignored URL components could still improve validation. |
| F7 | Users can copy MollySocket server parameters, which contain the password and endpoint, to the clipboard. | **Intentional credential export with limited lifetime.** This is an explicit user action for provisioning. The existing sensitive clipboard helper is used; API 30 synthetic instrumentation exercised clipboard behavior and expiry at 60 seconds. Android 13+ clipboard metadata and real MollySocket provisioning were not tested. |
| F7 | UnifiedPush key/value entries were included in the backup list. | **FIXED in prior patch series.** `UnifiedPushValues.getKeysToIncludeInBackup()` returns an empty list. API 30 synthetic instrumentation verified backup exclusion. The encrypted key/value store retains the MollySocket device password locally. |

## Evidence and tests

The focused receiver tests are in [UnifiedPushReceiverAvailabilityTest.kt](../../app/src/test/java/org/thoughtcrime/securesms/keyvalue/UnifiedPushReceiverAvailabilityTest.kt). They exercise actual receiver callbacks with a real `UnifiedPushValues` and `AccountValues.pushAvailable` backed by an in-memory `KeyValueStore`, a locked-state stub, and mocked network/distributor dependencies. They assert push availability falls from true to false, only the status key is written, endpoint/device/VAPID property getters are not touched by the callback, existing endpoint and credentials remain unchanged, and the network is restarted. An unlocked unregister case covers an already-absent endpoint. The same test class covers locked urgent notice preference behavior, malformed and `test:true` payloads, and connector rejection of missing or unknown registration tokens. These tests have been added but are **not yet run**; report their outcome only after Gradle executes them.

Historical synthetic Android evidence and local wire/transport probes are bundled under [reports/827/security/runtime](../../reports/827/security/runtime/README.md). The API 30 test run passed registration, endpoint changes, synthetic delivery, unregister handling, process restart persistence, backup exclusion, clipboard expiry, and missing-VAPID WebSocket fallback. It used a fake distributor with no Internet permission and an emulator firewall that denied external IPv4 and IPv6. It did not exercise a live Signal account, live Signal server, live MollySocket, a production distributor, or API 33+.

The registration request DTO and response mapping, compiled connector callback gate, linked-device server source contract, redirect settings, and OkHttp userinfo behavior have retained source, commands, and raw outputs in the same evidence directory. Exact claims and limits are recorded in its README and checksums.

## Remaining risks

The selected distributor can observe delivery metadata and can trigger fetches or false wake-ups. This architecture depends on the connector's unguessable local token and the user's distributor choice; the app does not perform sender-signature validation itself. Compromise of the configured MollySocket server or distributor is outside the confidentiality boundary supplied by UnifiedPush.

Locked callback behavior is source-changed and has focused automated tests, but those tests must pass before F4 can be marked complete. Physical-device behavior, Android 13+ clipboard privacy indicators, deployed-server compatibility, live device linking/removal, and air-gapped delivery remain unverified.
